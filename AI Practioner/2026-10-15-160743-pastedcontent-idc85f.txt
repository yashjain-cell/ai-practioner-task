  **Q1. How should repeated action items across meetings be handled?**          
                                                                                
  Treat the same underlying action item mentioned in multiple meetings as one   
  task, not multiple tasks. Store all relevant source-file references and the   
  meeting dates where it appears. If the wording or context indicates a         
  different task, create a separate item.                                       
                                                                                
  **Q2. Should a checked item in a later meeting close the earlier copy?**      
                                                                                
  Yes. If a later note marks the same action item as `[x]`, mark the existing   
  task as done, regardless of which meeting first introduced it. Preserve the   
  source references. Only update the task when the match is sufficiently        
  confident; do not automatically close ambiguous matches.                      
                                                                                
  **Q3. Which note formats should count as action items?**                      
                                                                                
  Support all three formats:                                                    
  - Markdown checkboxes such as `- [ ] Priya to send the revised quote`.        
  - Clearly identifiable action-item rows in tables.                            
  - Lines explicitly prefixed with `ACTION:`.                                   
                                                                                
  Normalize these formats into the same internal action-item structure. Ignore  
  ordinary prose that does not clearly represent an action item.                
                                                                                
  **Q4. What should happen when an item has no owner?**                         
                                                                                
  Keep the task and set its owner to `Unassigned`. Do not guess the owner.      
                                                                                
  **Q5. What should happen when an item has no due date?**                      
                                                                                
  Keep the task with a null due date. Do not invent a date. Such items should   
  appear in the open-task list but should not be marked overdue.                
                                                                                
  **Q6. How should relative due dates be interpreted?**                         
                                                                                
  Use the meeting date as the reference date, not the current system date.      
                                                                                
  - `by Friday`: the upcoming Friday, including today if the meeting is on      
  Friday.                                                                       
  - `next Tuesday`: the Tuesday of the following week, not the immediately      
  upcoming Tuesday.                                                             
  - `tomorrow`: the day after the meeting date.                                 
  - `today`: the meeting date.                                                  
  - `end of month`: the final calendar day of the meeting's month.              
  - Explicit calendar dates: use the specified date.                            
                                                                                
  Store the resolved date in ISO format (`YYYY-MM-DD`). If the due-date phrase  
  is ambiguous or unsupported, leave the due date null and report it rather     
  than guessing.                                                                
                                                                                
  **Q7. Where should email addresses come from?**                               
                                                                                
  Use a `people.yaml` file at the project root to map full names to email       
  addresses. Support full-name matching and use attendee information from       
  meeting notes when resolving owners. If multiple people share the same first  
  name and cannot be distinguished confidently, flag the ambiguity and do not   
  send a draft to an incorrectly identified person.                             
                                                                                
  If an owner has no configured email address, report that follow-up generation 
  cannot proceed for that owner.                                                
                                                                                
  **Q8. How should Gmail authentication work?**                                 
                                                                                
  Use the existing Gmail MCP connector if it is available and already           
  configured in the environment. Verify its available draft-creation            
  functionality before implementing the integration.                            
                                                                                
  Never hardcode credentials, request passwords in the CLI, or store access     
  tokens in source files. If Gmail MCP is unavailable or not authenticated,     
  show a clear error and document the setup requirement. Do not silently        
  substitute another integration.                                               
                                                                                
  The follow-up command must create a Gmail draft only. It must never send an   
  email.                                                                        
                                                                                
  **Additional implementation rules**                                           
                                                                                
  - Re-running ingestion must not create duplicate tasks.                       
  - Preserve source-file references for auditability.                           
  - Overdue means an item is open, has a due date, and its due date is earlier  
  than today's date.                                                            
  - Use the local system date for overdue filtering, while using the meeting    
  date to resolve relative dates.                                               
  - Malformed files or entries should be reported and skipped where necessary,  
  without stopping ingestion of valid files.                                    
  - Update the specification, implementation plan, and task checklist to        
  reflect these decisions.                                                      
  - Add tests for duplicate detection, completion propagation, relative dates,  
  ambiguous owners, missing data, and malformed notes.

  remaining unresolved questions. Do not start implementation until the SDD     
  documents are updated.
